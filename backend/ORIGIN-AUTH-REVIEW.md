# Origin authentication: review and activation plan

Status: development only. No production activation, credentials, infrastructure
changes or remote origin-restriction experiment. Base main:
`2a20f9993918c1a0e99127a1aa2886e2a48d8667`.

## Contract

`ORIGIN_AUTH_ENABLED` defaults to disabled when absent. Only literal `true`
and `false` are accepted; any other configured flag fails startup. Enabled mode
requires `ORIGIN_AUTH_SECRET` to be exactly 64 lowercase hexadecimal characters
(32 randomly generated bytes). Invalid or absent required configuration throws a
generic error before listening; it never silently disables the gate. Disabled
mode ignores an unused secret, enabling rollback without deleting credentials.
Configuration is captured at startup; changes require a compatible deployment.
Never use the documented examples as credentials; generate outside Git with a
secure tool, store in Render and the restricted Cloudflare rule only.

The first app middleware checks `X-TecnoDesk-Origin-Auth`, before Helmet, CORS,
OPTIONS responses, client-IP selection, body parsing, rate limits and Prisma.
Exactly one raw header field with an exact matching value is required. Duplicate
fields (including differently cased names), arrays, comma-separated values,
incorrect lengths or non-hex values are rejected. Fixed-length valid candidates
use Node `timingSafeEqual`. Rejections return generic HTTP 403, no-store and
noindex; they do not log headers, addresses, paths, tokens or credentials.
Only exact-path GET /health is exempt (query does not alter the path). HEAD,
OPTIONS, /health/ and /api/health are not exempt. Invalid startup configuration
also prevents liveness from starting: deliberately fail closed, not a healthy
but unprotected deployment.

Neither CLIENT_IP_MODE nor existing limiter settings change. The secret proves
knowledge of a private credential; CF-Connecting-IP, XFF, Host, UA and Origin
are not evidence of origin authorization. It must not replace JWT, Turnstile,
endpoint permissions, input validation or application rate limiting. An attacker
who obtains the secret could replay it: restriction of administrative access and
rotation remain necessary. It is not a signed per-request proof or mTLS.

## Isolated automated evidence

`npm run test:origin-auth` executes configuration validation and the real Express
app over loopback in separate enabled, explicitly-disabled and default processes.
Prisma is simulated before requests; DATABASE_URL uses loopback port 1, never a
real database. Credentials are random in memory only; fixture links, images and
RFC documentation IPs contain no real customer data.

The tests cover successful readiness and previews/images, missing/incorrect/
duplicate credentials, comma values, false IP headers, preflight before CORS,
malformed body before parsing, the exact liveness exemption, absent/invalid
configuration, default/disabled compatibility, and absence of the secret from
captured logs/responses. Unauthorized readiness/preview/image requests cannot
reach Prisma. A global budget of one and subsequent successful image also prove
rejected requests do not spend normal API budget. The existing client-IP,
password-reset, preview fairness, tracking, health and CI regressions remain.
Local tests do not prove that Cloudflare overwrites headers or that disabling a
Render hostname preserves actual routing/monitoring.

## Existing laboratory and blocking dependencies

Read-only Render inventory confirms independent Backend 2
`tecnodesk-proxy-ip-staging`, Free, repository
`marcosgradac/tecnodesk-proxy-ip-staging`, autodeploy off, /health configured,
Render hostname enabled. The owner previously confirmed the independent proxied
hostname `ip-staging.tecnodeskpro.com`. Its IP-diagnostic code does not include
this new gate. No secret was accessed and no Render/Cloudflare operation was
performed in this task. Local laboratory documentation is older than the latest
infrastructure results and is not treated as proof of its currently running code.

Before remote validation, prepare/review a laboratory-only adapter containing the
same gate, deploy to Backend 2 with a new lab-only credential, verify custom
hostname and Free quotas, and configure a Transform Rule scoped exactly to the
lab hostname. These dependencies are not satisfied by the current TecnoDesk PR;
no test is improvised against production. Do not reuse a production credential
or deploy the functional TecnoDesk application to the lab.

New, narrowly scoped acceptance checks (do not repeat 4K/4N):
1. Enable the lab gate after a working Set static rule is verified. Configure the
   rule to overwrite this private header, never append and never reflect it in
   response headers. Keep HTTPS Full (strict); do not add WAF bypass rules.
2. A normal proxied request and one with a false supplied credential succeed;
   validate overwrite at the protected origin, without dumping request headers.
3. Direct Render requests with absent/wrong credential and synthetic XFF/CF
   fail 403 before the lab handler. A controlled trusted request proves the lab
   itself is healthy. Secret inputs are secure and never printed or persisted.
4. Check OPTIONS through the proxy, readiness, dummy OG/image and platform
   liveness. Record only HTTP outcomes and handler counts, no IPs or credentials.
5. Only on the independent lab, disable its Render subdomain after confirming a
   verified custom domain and a restoration path. Direct hostname must return
   platform 404 while the proxied hostname and Render health remain working.
6. Restore the lab restriction/configuration if an unexpected error appears.

## Production prerequisites and activation order (requires new approval)

1. Inventory Vercel Production and Preview API destinations, historical frontend
   deployments/cached bundles, external clients, monitors, scripts and any provider
   callbacks. No payment webhook handlers were found in the reviewed backend;
   external dashboard settings still require owner verification. Update clients
   to api.tecnodeskpro.com; callers do not receive the private secret.
2. Migrate Preview VITE_API_URL from onrender to api.tecnodeskpro.com or an approved
   independent staging API. Preserve Preview authentication/CORS and other env
   values. This task makes no Vercel change. Production already uses the custom
   API; both WhatsApp/Facebook rewrites do too. Slug/token reconstruction and SPA
   fallback remain unchanged. No UA trust exemption is added to the gate.
3. Set PUBLIC_API_ORIGIN=https://api.tecnodeskpro.com with a separately approved
   deployment so generated relative business logos stop using the onrender
   fallback. Inventory any stored absolute onrender images/links: changing the
   origin does not rewrite those. Resolve them without unapproved data changes.
   Check fictional OG metadata plus an image, not real tracking tokens.
4. Deploy the reviewed gate disabled. Store the new credential securely in Render
   and configure Cloudflare Set static for http.host eq "api.tecnodeskpro.com",
   all paths/methods. Verify the rule is active and no later transform overwrites
   it. JWT Authorization and Turnstile headers are untouched. Do not expose the
   secret via VITE_, Git, CLI arguments, responses, logs or support screenshots.
5. With isolated evidence and restored deployment references available, enable
   ORIGIN_AUTH_ENABLED=true in an explicitly approved deployment. Absent secret
   is a startup failure. Confirm HTTPS/OPTIONS, fictional OG/logo, readiness and
   Render's actual health check. Render currently reports an empty healthCheckPath
   for Backend 1: confirm platform monitoring configuration before enabling;
   propose explicit /health separately, never assume it is already configured.
6. Disable the production onrender subdomain only after consumers are migrated
   and origin authorization is confirmed. Render documents platform 404 without
   forwarding to the app. Test the custom-domain route still works; retain DNS
   CNAME to Render as prescribed by its custom-domain integration.

## Reversal

Record previous public env values, rule state, subdomain policy and compatible
successful deployment IDs before activation. For a failed cutover, re-enable
onrender if needed, restore ORIGIN_AUTH_ENABLED=false with a compatible deployment,
then restore affected API/image consumer settings and deployments in a coordinated
order. The unused injected header can remain during rollback. Never remove the
Cloudflare header while the backend still requires it; that blocks valid traffic.
Do not rollback to code lacking the gate while claiming the origin is protected.
For credential rotation, disable the gate only in an approved maintenance plan,
or separately design/test a bounded old/new overlap; this PR supports one secret.

## Costs, limits and decision

Uses one Cloudflare Free Transform Rule (10 active rules documented; verify actual
remaining quota), existing custom domain and existing Render service. No Worker,
new paid service or dependency. Lab domain quotas/build/bandwidth must still be
checked before infra work. A static rule contains a secret visible to authorized
Cloudflare administrators/API readers: restrict access and backups accordingly.

Application 403 still incurs connection/Express overhead; only Render's disabled
hostname blocks that path before the app. Direct custom-domain origin routing
must also reject missing credentials in the isolated test. GET /health remains
an intentional small public exception without DB. This is not absolute volumetric
DDoS protection and does not fix baseline proxy IP sharing. GO for code review;
NO-GO for production activation until remote lab evidence, consumer migration,
monitoring and rollback readiness are approved.
